# Internationalization (i18n) - Design Spec

## 1) Product Goal

Add multilingual support to the entire Sky Companion app using `@nuxtjs/i18n`, with English as default and Vietnamese as the second language.

The system must be scalable so future languages (`ja`, `zh`, `fr`, `de`, `es`) can be added by configuration and locale files, without changing domain/business logic.

## 2) Confirmed Decisions

- I18n framework: `@nuxtjs/i18n`.
- Default language: `en` (English).
- Initial supported languages: `en`, `vi`.
- URL strategy: `no_prefix` (no locale prefix in route paths).
- Localization scope: all visible UI text + all user-facing errors/messages (B2).
- Units: implement user-toggleable `metric` / `imperial` (U2).
- AI language: always derived from current app locale and sent in every Sky AI request.
- Rule: no hardcoded user-visible text in pages/components/composables that render to users.

## 3) Scope

### In Scope

- Configure and integrate `@nuxtjs/i18n` globally in Nuxt.
- Introduce locale files:
  - `locales/en.json`
  - `locales/vi.json`
- Refactor all pages to use translation keys:
  - `/`
  - `/moon-calendar`
  - `/telescope`
  - `/meteor-showers`
  - `/astrophotography`
  - `/iss`
  - `/compass`
  - `/ai/*` pages
- Refactor shared components to use i18n keys for visible text.
- Locale-aware formatting for date/time/weekday/month using `Intl` based on current locale.
- Add units architecture and a UI toggle for `metric` vs `imperial`.
- Ensure user-facing error strings are localized.
- Ensure Sky AI request always includes current language in a stable, typed way.

### Out of Scope (now)

- Translating developer-only logs/debug output.
- Full linguistic localization of AI model prompt engineering beyond selected language field.
- Region-specific defaults beyond `en`/`vi` (future extension).

## 4) Architecture

```text
nuxt.config.ts
  └── @nuxtjs/i18n module config
        ├── defaultLocale: en
        ├── strategy: no_prefix
        └── locales: [{ code, name, file }, ...]

locales/
  ├── en.json
  └── vi.json

app/composables/
  ├── useAppLocale.ts     # locale state + persistence helpers
  ├── useUnits.ts         # metric/imperial state + persistence
  └── useFormatters.ts    # locale-aware date/time/number formatters

app/components/** + app/pages/**
  └── use t(...) / $t(...) only for user-facing text

app/composables/useSkyAI.ts
  └── send language from current locale (typed)
```

### Principles

- Keep i18n concerns centralized in composables/config, not duplicated by page.
- Keep conversion/formatting logic in helpers; components only render.
- Locale expansion must be additive (new locale entry + new JSON file).
- No route/path changes when user changes locale (as requested by `no_prefix`).

## 5) Folder & File Changes

```text
nuxt.config.ts                         # add @nuxtjs/i18n module + i18n options
locales/en.json                        # new
locales/vi.json                        # new
app/composables/useAppLocale.ts        # new
app/composables/useUnits.ts            # new
app/composables/useFormatters.ts       # new
app/components/settings/LanguageSwitcher.vue   # new (or equivalent shared UI)
app/components/settings/UnitSwitcher.vue       # new (or equivalent shared UI)
app/pages/**/*.vue                     # migrate hardcoded strings
app/components/**/*.vue                # migrate hardcoded strings
app/composables/useSkyAI.ts            # bind AI language to active locale
types/ai.ts                            # keep strict locale-aware language typing
```

Notes:

- Exact placement of switcher components may follow existing project layout patterns.
- If existing shared header/settings area exists, switchers should be integrated there instead of creating duplicated controls per page.

## 6) Translation Schema

Use consistent namespaces to avoid key collisions and enable scalable additions:

```json
{
  "common": {
    "loading": "...",
    "retry": "...",
    "close": "...",
    "unknownError": "..."
  },
  "nav": {
    "home": "...",
    "moonCalendar": "...",
    "telescope": "..."
  },
  "pages": {
    "home": { "...": "..." },
    "moonCalendar": { "...": "..." },
    "telescope": { "...": "..." },
    "meteorShowers": { "...": "..." },
    "astrophotography": { "...": "..." }
  },
  "components": {
    "skyAI": { "...": "..." }
  },
  "errors": {
    "ai": {
      "missingAstronomyData": "...",
      "explainFailed": "..."
    }
  },
  "units": {
    "metric": "Metric",
    "imperial": "Imperial",
    "temperature": {
      "celsius": "degC",
      "fahrenheit": "degF"
    },
    "distance": {
      "km": "km",
      "mi": "mi"
    }
  }
}
```

Key policy:

- Reuse `common.*` where meaning is truly shared.
- Use page/component-specific namespaces for domain text.
- Do not encode business values in sentence keys.

## 7) Locale, Date/Time, and Number Formatting

### Locale source of truth

- Use the i18n locale ref from `@nuxtjs/i18n` as single source.
- Persist selected locale via i18n cookie + localStorage helper for smooth client hydration behavior.

### Formatter design

`useFormatters()` exposes stable formatting helpers:

- `formatDate(date)`
- `formatTime(date)`
- `formatWeekday(date)`
- `formatMonth(date)`
- `formatDateTime(date)`
- `formatNumber(value, options?)`

All helpers internally use `Intl.*` with current locale so language switch updates all outputs consistently.

## 8) Units System (Metric/Imperial)

### State

- `useUnits()` stores one of: `metric | imperial`.
- Default: `metric` (explicit project default for now).
- Persist preference in localStorage.

### API

- `unitSystem` ref
- `setUnitSystem(system)`
- conversion helpers:
  - `formatDistanceKm(km)` -> `km` or `mi`
  - `formatTemperatureC(c)` -> `degC` or `degF`

### Rendering rule

- Components display values through unit helpers only.
- Unit labels come from translation files (`units.*`) and never hardcoded in UI.

## 9) Sky AI Language Behavior

- Replace hardcoded `language="en"` usage in pages/components.
- `useSkyAI` takes current locale-derived language and sends it in request body.
- Map must be explicit and typed:
  - `en` -> `en`
  - `vi` -> `vi`
- Server API schema keeps validating language enum (`en` | `vi`) for request safety.

Future extension:

- When adding new locales, AI-language mapping is extended in one place without touching page logic.

## 10) Error Handling (Localized User-Facing Messages)

- For composables/components, user-visible errors must reference i18n keys.
- For server-returned friendly messages, prefer returning error code/key and translate in UI.
- If current flow requires plain message string from server, map to i18n key at boundary before displaying.

Fallback rule:

- Missing key should not crash rendering; fallback to English key path/value while logging warning in dev mode.

## 11) Rollout Plan

1. Install and configure `@nuxtjs/i18n`.
2. Create `en.json` / `vi.json` baseline dictionaries.
3. Add locale + units composables and switcher UI.
4. Refactor shared components first (highest reuse), then pages.
5. Refactor Sky AI language binding and localized errors.
6. Run typecheck/tests and hardcoded-text pass.

## 12) Testing Strategy

### Automated

- Unit tests for:
  - locale-aware date/time formatting (`en`, `vi`)
  - unit conversions (`km`/`mi`, `degC`/`degF`)
  - locale and units persistence
  - Sky AI request includes expected language
- Existing tests should pass without regression.

### Verification checklist

- Switch language to Vietnamese and verify all major pages/components update text.
- Switch back to English and verify fallback/default behavior.
- Confirm date/time/weekday/month render changes by locale.
- Confirm unit toggle updates all relevant displays.
- Confirm no user-facing hardcoded strings remain in migrated files.

## 13) Risks & Mitigations

- Risk: hidden hardcoded strings in deeply nested components.
  - Mitigation: grep-based sweep + migration checklist per page group.
- Risk: inconsistent number/date formatting across components.
  - Mitigation: enforce shared `useFormatters()` helpers.
- Risk: unit conversion drift across pages.
  - Mitigation: centralize conversions in `useUnits()` / unit formatter utilities.
- Risk: AI language mismatch when locale changes quickly.
  - Mitigation: derive language from reactive locale at request time.

## 14) Acceptance Criteria

- `@nuxtjs/i18n` is integrated with default `en`, supported `en` and `vi`.
- Locale strategy is `no_prefix`; routes stay unchanged.
- All visible text and user-facing errors are served through translation keys.
- Date/time/weekday/month display follows currently selected locale.
- Unit toggle exists and updates supported unit displays (`km/mi`, `degC/degF`).
- Sky AI always receives language matching current user locale.
- Architecture allows adding `ja`, `zh`, `fr`, `de`, `es` by config + locale files, without changing business logic.
